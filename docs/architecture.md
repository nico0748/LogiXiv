# アーキテクチャ

## データモデル

いちばん効いている判断は、**構造データと注釈データを分けた**こと。

```
PaperDocument
├── structure    PDF から機械的に得られるもの（文・座標・節）。再解析で作り直される
└── annotations  人と Claude が積み上げるもの（訳・メモ・用語集・訳さない記録・
                 文の区切りの直し）。作り直されない
```

両者は文の **正規化ハッシュ**で結び付く。`annotations.translations` のキーは
文の ID でも通し番号でもなく、本文から計算したハッシュである。

```
正規化 = NFC → soft hyphen 除去 → 引用符の ASCII 化 → 文字間ハイフンの除去 → 空白畳み込み
hash   = sha256(正規化テキスト).slice(0, 16)
```

規則ごとの理由:

| 規則 | 理由 |
| --- | --- |
| NFKC ではなく **NFC** | NFKC は上付き・℃・µ・合字・ローマ数字を潰す。`We set x² = 2.` と `We set x2 = 2.` が同じハッシュになり、**別の文に別の文の訳が付く** |
| ダッシュの種類は**保つ** | en dash（範囲 A–B）と hyphen（複合語 A-B）は別物。まとめて `-` に寄せると衝突する。em dash を `-` にすると `model— however` が `modelhowever` に融合する事故も起きる |
| 文字間のハイフンは**落とす** | GROBID は折り返しを解決した `block-sparse` を返すが、pdf.js 経由のフォールバックは行末で割れた `block-` + `sparse` を見る。どちらも `blocksparse` に正規化されるので、**GROBID を後から立ち上げて再解析しても訳が外れない**。代償は `re-cover` と `recover` が同じハッシュになること |

正規化規則を変えたときは `STRUCTURE_VERSION`（`packages/core/src/hash.ts`）を上げ、
`packages/core/src/migrate.ts` に移行を書く。構造には原文が残っているので
「旧ハッシュ → 原文 → 新ハッシュ」の対応表を作れば注釈は付け替えられる。
移行は `DocumentStore.read` が読み出し時に自動で行い、結果を書き戻す。

この設計のおかげで、

- GROBID を後から入れて再解析しても訳が消えない
- 文の順番が変わっても注釈がずれない
- 他人の書き出しを取り込むと、同じ文にだけ訳が乗る

同じ文が同じ論文に 2 回現れると訳を共有する。原文が同一なら訳も同一で構わない、という割り切り。

## 解析の 2 経路

```
PDF ─┬─ GROBID (segmentSentences=1, teiCoordinates=s) ─→ 文 + PDF座標  ← 本命
     └─ pdf.js テキスト抽出 → 行組み立て → 文分割      ← フォールバック
```

GROBID 経路では、`<figure>` / `<table>` / `<formula>` / `<note>` / `<listBibl>` の中の `<s>` を
本文から外す。素通しすると図キャプション・表のセルの数値・脚注・数式が「文」として
サイドバーに並び、order も本文と入り混じる。

### フォールバック経路のレイアウト解析

pdf.js が返すのは「文字片と座標」だけなので、行より上の構造は自分で復元する。
手順は **段を見つける → 行にする → 行の役割を決める → 本文だけ連結して文に割る**（`packages/core/src/layout.ts`）。

1. **段組の検出**: 文字の x 範囲を 1 次元に射影し、「ほとんどの行で空いている帯」を段間とみなす。
   これが無いと左右の段が同じ y で 1 行に連結され、本文が交互に混ざる。
   実測で、正解の文が取れた割合が 1 段組 60% に対し 2 段組は **30%** まで落ちていた。
2. **行の役割**:
   - *柱・ノンブル* … 上下端に近く、**本文ブロックから一行ぶん以上離れて**いて、
     複数ページに繰り返し出るもの。位置だけで切ると本文の 1 行目まで消える（実際に消していた）
   - *見出し* … 既知の章名・番号つき見出し・本文より大きい文字で、短く終端が無い行。
     節として登録し、本文の文には混ぜない
   - *図表キャプション・参考文献・別行立ての数式* … 本文から外す。
     数式は「英字比率が 0.65 未満 かつ 演算子を含む かつ 短い」で判定する
     （短さを条件から外すと、インライン数式を含む本文の折り返し行まで落ちる）
3. **ハイフネーション**: 行末のハイフンは、同じ文書の行の途中に同じ複合語が現れるかで
   落とすかどうかを決める。段やページをまたぐ行では結合しない。

現在の実測値（`npm run measure`）は 1 段組・2 段組とも再現率 100% / 混入 0。
それでも複雑なレイアウト（表の中の文、回り込み、脚注の多い組版）では崩れる。

フォールバックは 2 段組で読み順が崩れ、数式や脚注が本文に混ざる。
pdf.js は Node では同一スレッドの「fake worker」として動くので、**ワーカースレッドに逃がしてある**。
逃がす前は 900 ページの PDF 1 本でイベントループが 68 秒止まり、その間の keep-alive 接続が
切られて他のクライアントが ECONNRESET を受けていた。ページ数・文字片数・実時間の
3 つに上限を置き、同時解析数も 2 に絞っている。
**どちらで解析したかを隠さない**のが方針で、`structure.parser` と `structure.parserNote` が
UI のバッジと注記に直結している。黙って劣化させるのがいちばん質が悪い。

GROBID 呼び出しで意図的に指定しているパラメータ:

| パラメータ | 値 | 理由 |
| --- | --- | --- |
| `segmentSentences` | 1 | `<s>` を出させる。1 文リーダーの前提 |
| `teiCoordinates` | s | `<s>` に PDF 座標を付けさせる |
| `consolidateHeader` | 0 | 既定値 1 は CrossRef へ問い合わせる。未公開原稿のタイトルを外に出さない |
| `consolidateCitations` | 0 | 同上（参考文献も外に出さない） |

## 座標系

GROBID の `coords` は **PDF ユーザー空間・左上原点**。pdf.js は左下原点なので、
フォールバック経路では `y = pageHeight - baseline - height` で揃えてある。
描画側は「表示幅 ÷ ページ幅」という単一の倍率しか持たないので、拡大しても対応が崩れない。

## 保存

```
~/.logixiv/
└── documents/
    └── doc_xxxxxxxx/
        ├── document.json   構造 + 注釈
        └── source.pdf      元 PDF
```

DB を使わないのは、「アプリを捨ててもデータが読める」ことを優先したから。
書き込みは常に一時ファイル → `rename`（同一ディレクトリなので原子的）。
JSON を書いている途中で落ちても、前のバージョンがそのまま残る。

同時更新は文書 ID ごとの Promise チェーンで直列化する。`update()` は
読み → 変更 → 書き を 1 つのロックに収めるので、ブラウザと Claude が同時に
書いても片方の変更が消えない。

## 文の区切りの手直し

文分割は「迷ったら切る」側に倒してある（切りすぎは画面上ですぐ分かるが、
2 文が 1 枚のカードに同居すると対訳の 1 対 1 対応そのものが壊れるため）。
そのぶん手で直せる必要がある。

直し方は 2 つだけ。連続する文の**結合**と、1 文の文字位置での**分割**。

設計上の要点は 3 つ。

1. **結果は構造に焼き込み、手順は注釈に残す**（`annotations.sentenceEdits`）。
   構造だけ直すと再解析で元に戻り、手順だけ持つと読み出しのたびに再計算が要る。
   両方持てば、再解析のときだけ手順を流し直せばよい（`applyStructure`）。
   当てられなくなった手順は記録から外す。残すと毎回失敗し続ける。
2. **対象は hash で指し、一致する箇所すべてに適用する**。訳は hash に付くので、
   同じ本文が 2 か所にあるとき片方だけ区切りが違うと、一方の訳がもう一方に
   出ない・進捗が合わない、といった説明のつかない状態になる。
3. **取り消しに再解析を要求しない**。結合の逆は分割、分割の逆は結合なので、
   適用時に逆向きの情報（`undo`）を記録しておけば、その場で戻せる。
   再解析は数十秒かかるので、そこを通す設計は実質「戻せない」と同じ。

記録は hash ではなく**原文テキスト**（`sourceTexts`）を持つ。正規化規則を変えた
ときに hash を付け替えられるのは、構造に原文が残っているからだが、編集前の文は
もう構造に無い（結合・分割済みの姿しか残っていない）。原文を持っていれば、
新しい規則で計算し直すだけで済む。

分割を戻すときは「元は空白で区切られていたか」（`undo.joiners`）まで見る。
単語の途中で切った文を空白 1 個で繋ぎ直すと、`method.` が `me thod.` になり、
別の本文として扱われて訳が静かにはぐれる。再解析で適用し直したときは、
取り消し情報も**そのときの本文に合わせて作り直す**。同じ hash でも綴りの長さは
変わりうるため（`block- sparse` → `block-sparse`）、古い位置のまま戻すと
関係ない場所で切ってしまう。

区切りを変えると当然ハッシュが変わり、元の文に付いていた訳は宙に浮く。
消さずに残してあるので、取り消せばそのまま戻る。

## マージ規則（訳とメモで非対称）

| 対象 | 規則 | 理由 |
| --- | --- | --- |
| 訳 | 人手修正済み > 機械訳。同じ種別なら新しい方が勝つ | 訳は正解が 1 つに収束するもの |
| メモ | 消さない。本文が同じものだけ重複として弾く。ID 衝突は振り直して両方残す | メモは多いほど良いもの |
| 用語集 | 未登録の語だけ足す | 既存の判断を上書きしない |

取り込み先に無い文の注釈は、既定では捨てて件数を報告する（`orphanPolicy: 'drop'`）。
これは**書き出し HTML の取り込み専用**の規則。

再解析（`applyStructure`）はマージを通さない。構造だけ差し替え、注釈は
`annotations` にそのまま残す（ハッシュで自動的に再結合される）。対応する文が
見つからなかった注釈も削除しない — GROBID のバージョン差で文が一時的に消えることがあるため。

再解析は数十秒かかるので、**構造の適用は必ず `store.update` の中**（最新を読み直した後）で行う。
ロックの外で読んだ文書に書き戻すと、解析中に届いた翻訳やメモが 200 を返して受理された後に
黙って消える。削除済みの文書に書き戻して「PDF の無いゾンビ文書」を復活させないよう、
`store.update` は途中で文書が消えていたら `DocumentMissingError` を投げる。

## 書き出し HTML

```
<style>   静的フォールバック用 + ビューア用
<div id="lx-root">      ← ビューアがここに描く
<div id="lx-static">    ← 対訳とメモの素の HTML。ビューア起動時に消える
<script type="application/json" id="logixiv-data">  ← 構造 + 注釈 + PDF(base64)
<script>  ← ビューア本体（pdf.js 同梱、IIFE 1 本）
```

外部 URL の参照はゼロ。ネットワークが無い環境でも、査読中の匿名環境でも、
10 年後でも開けることを狙っている（`npm run test:e2e` が外部参照ゼロを検査する）。

取り込み側は **埋め込み JS を絶対に実行しない**。該当の script 要素を切り出して
`JSON.parse` するだけで、DOM も作らず `eval` も使わない。
書き出しは人づてに回るファイルなので、実行経路を残さない。

注釈に `</script><img onerror=...>` を書かれても壊れないよう、静的フォールバックは
全テキストを HTML エスケープし、JSON 側は `<` と `>` を `\u003c` / `\u003e` に、
U+2028 / U+2029 もエスケープしてある（ユニットテストで検査している）。

**取り込む JSON は全部検証してから使う**（`packages/core/src/validate.ts`）。
型アサーションで通していた頃は、`annotations: null` を仕込んだ HTML を 1 回取り込むだけで
一覧 API が恒久的に 500 になり、ディスクに残るので再起動しても直らなかった。
検証では文のハッシュも**受け取った値を使わず原文から計算し直す** —
ここを外部入力に委ねると「別の文の訳が付く」状態を外から作り込める。

該当する `<script id="logixiv-data">` が複数あったら、黙って先頭を採らずエラーにする。
本物の前に偽のデータを置いた HTML を配られる経路を残さないため。
探索は正規表現ではなく線形スキャン（`<script[^>]*id=...` は一致しない入力で
バックトラックし、入力長に対して二次で劣化する＝誤ったファイルを投げたときに固まる）。

## ローカル前提のセキュリティ

- 既定で `127.0.0.1` にのみ bind する。`--host` で変えると起動時に警告を出す
- `Host` / `Origin` ヘッダを検証し、localhost 以外と **Host 無し**を 403 で弾く（DNS リバインディング対策）
- 全レスポンスに `X-Content-Type-Options: nosniff` と `X-Frame-Options: DENY`
- 書き込み系の入力は全フィールドの型と長さを HTTP 層で確認する
- 文書 ID は `^[A-Za-z0-9_-]{1,64}$` に限定し、パスに使う前に検証する
- 静的配信はルート外へ出るパスを弾く
- アップロードは 100MB 上限、先頭 4 バイトが `%PDF` でなければ受け付けない

## SSE

Claude が MCP 経由で訳を書いた瞬間にブラウザが更新されるのは、このツールの体験の中心。
そのためポーリングではなく SSE で push している。MCP サーバーがファイルを直接触らず
HTTP 越しに本体へ話しかけるのも、書き手を 1 プロセスに集めてこの通知を確実にするため。

購読者が読まない場合は**イベントを捨ててその購読者を切る**。`write()` の戻り値を
無視していた頃は、`/api/events` を開いて放置するだけでメモリを無限に伸ばせた。
取りこぼしても壊れない設計（クライアントは再接続して文書全体を取り直す）なので、
詰まった購読者は落として構わない。

ブラウザ側はイベントを 300ms で合体させてから 1 回だけ取り直す。
イベント 1 件ごとに全文を取り直していた頃は、リーダーを開いているだけで
Claude の 100 文の書き込みが 3.3 秒 → 20.6 秒に伸びていた。
