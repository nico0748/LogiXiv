# 処理速度の改善: Go への移行の検討と要件定義

PaperLens のロジック部分を Go に移せば速くなるかを、実測をもとに検討した記録と、その結果決めた改善の要件。
計測は Apple M3（8 コア）、Node 22.9、Go 1.27.3。計測中は他の負荷があり（load average 8〜14）、絶対値は 1.5〜3 倍ほど膨らんでいる。比較は同じ条件で交互に流した値で行った。

## 結論

**Go には移さない。TypeScript のまま、遅さの原因（毎回すべてのファイルを読み直して解析し直す作り、起動時の pdf.js の読み込み）を直す。**

- 遅い処理の大半は言語ではなく作りが原因で、Go に移しても数倍、キャッシュなら数十〜百倍速くなる。
- 時間の 6〜8 割を占める PDF の文字抽出と描画は pdf.js が行っており、Go には pdf.js と同じ文字列・座標を出すライブラリが無い。差し替えると、既存の `sentences.json` の文のハッシュとマーカーの位置がずれ、画面（ブラウザの pdf.js）とも食い違う。
- `packages/core` と `src/lib` は画面・ローカルサーバー・MCP サーバーで共有している。一部を Go にすると同じロジックを 2 つの言語で保守することになる。

## 調べた箇所と実測

### 1. 論文をまたぐ集計（単語帳・グラフ・検索・論文一覧）

論文 300 本の合成データ（実データ 3 本を複製）での 1 回あたりの時間。

| 処理 | 3 本 | 50 本 | 300 本 | 1000 本 |
|---|---|---|---|---|
| 論文一覧 `/api/papers` | 1.4 ms | 19 ms | 131 ms | 381 ms |
| 単語帳・数式帳 `/api/lists` | 11 ms | 196 ms | **1072 ms** | 8264 ms |
| グラフ `/api/graph` | 3 ms | 42 ms | 255 ms | 1050 ms |
| 検索 `/api/search`（該当なし） | 3 ms | 47 ms | 292 ms | 1232 ms |

単語帳の集計を 3 通りで比べた（300 本）。

| 実装 | 時間 |
|---|---|
| 現状の TypeScript | 1.0〜1.3 s |
| Go（`encoding/json`、逐次） | 0.63〜0.93 s |
| Go（8 goroutine） | 0.15〜0.35 s |
| TypeScript ＋ 更新時刻でのキャッシュ（2 回目以降） | **8〜14 ms** |

原因は、`sentences.json`（1 本 350 KB 前後、日本語が多い）を毎回すべて読み、UTF-8 の復号と `JSON.parse` をしていること。用語集（`annotations.glossary`）を取り出すためだけに全体を解析している。

### 2. MCP サーバー

- 起動（`initialize` 〜 `tools/list`）: 中央値 0.45〜0.65 s。そのうち約 190 ms は pdf.js の読み込みで、その大半は pdf.js が読み込む `@napi-rs/canvas` のシステムフォント走査。MCP SDK・zod など残りの依存は合わせて約 125 ms。
- 読み取りツールは 1 回 1〜30 ms。エージェントの 1 往復（数秒）に比べて小さい。
- `list_papers` は全論文の `sentences.json` を毎回解析して進み具合を出すため 30〜90 ms かかり、論文の数に比例して伸びる。
- `get_page_image` は 0.13〜1.3 s で、pdf.js の描画と Skia の PNG 変換がほぼすべて。Go の `image/png` は Skia より速くない。
- 本文の最初の抽出（`read_paper_text`）は 0.3〜1 s。2 回目以降はキャッシュから 1 ms 前後。

### 3. 取り込みと文分割

| PDF | 合計 | うち pdf.js | うち Go に移せる純粋な計算 |
|---|---|---|---|
| 2302.12173v2（33 ページ） | 約 1.66 s | 約 1.0 s | 約 0.48 s（29%） |
| IJCNN2026_Kawai（7 ページ） | 約 1.44 s | 約 1.1 s | 約 0.30 s（21%） |
| frai-7-1451926（15 ページ） | 約 1.97 s | 約 1.5 s | 約 0.38 s（19%） |

- Go が 2〜5 倍速くても縮むのは 0.2〜0.35 s で、しかも論文 1 本につき 1 回だけ（結果は `sentences.json` に残る）。
- 移す対象は約 3,000 行の細かい規則（`layout.ts`、`sentences.ts` など）。文字位置を JavaScript の UTF-16 単位で数えているため、Go で同じ結果を出すには UTF-16 の扱いをそっくり再現する必要がある。

### 4. Go 側で使える部品

| 用途 | 候補 | 評価 |
|---|---|---|
| MCP | 公式 `modelcontextprotocol/go-sdk` v1.8 | 十分使える。ただし移す手間の本体は SDK ではなく、裏のロジック |
| PDF の文字と座標 | pdfcpu / ledongthuc/pdf | 文字の配置付き抽出が無い、または弱い |
| | unidoc/unipdf | 商用ライセンス（キーが必要） |
| | go-fitz（MuPDF） | AGPL。アプリ全体が AGPL になる |
| | go-pdfium（WebAssembly） | ライセンスは問題ないが、文字の区切り方が pdf.js と違う |
| 描画 | go-pdfium | 使えるが、pdf.js と PDFium の 2 つのエンジンを抱えることになる |

## 要件定義

### 目的

出力（API と MCP の応答、保存するファイル）を 1 バイトも変えずに、次の 2 点を速くする。

1. ローカルサーバーと MCP サーバーの起動
2. 論文をまたいで集計する処理（論文一覧、単語帳・数式帳、グラフ、検索、`list_papers` の進み具合）

### 機能要件

- **R1 pdf.js の遅延読み込み**: `server/pdftext.ts`・`render.ts`・`service.ts`・`slides.ts` は、pdf.js を最初に使うときに読み込む。PDF を扱わない処理（起動、一覧、ノートの読み書き）では読み込まない。
- **R2 読み取り結果のキャッシュ**: 保管庫のファイルから作った値を、ファイルの識別子（inode・更新時刻（ns）・大きさ）が変わるまで使い回す。
  - 対象は、論文一覧の frontmatter 要約、`paperlens.json` の注釈（読むだけの集計用）、`sentences.json` の用語集と対訳の進み具合、検索用に折りたたんだノートの行。
  - 判定は読むたびに `stat` で行う。ほかのプロセス（MCP サーバー、Obsidian）が書き換えても次の読み取りで作り直す。
  - キャッシュした値は呼び出し側で書き換えない（読み取り専用の経路でだけ使う）。書き込みの経路（`changeAnnotations`、`mutate` など）は今までどおり毎回ファイルを読む。
  - 件数に上限を設け、古いものから捨てる。
- **R3 互換**: `Vault` を実装するほかの保管庫（ブラウザ版の `FsVault`、メモリ上の保管庫）はキャッシュなしで今までどおり動く。

### 非機能要件と受け入れ基準

- 変更の前後で、論文 50 本のデータに対する HTTP（論文一覧・単語帳・グラフ・検索・各論文の詳細・対訳・注釈）と MCP（`tools/list`、`list_papers`、`get_lists`、`get_graph`、`search_notes`、`search_sentences`、`get_sentence_outline`、`read_paper_text`、`find_in_paper`）の応答が完全に一致する。
- 既存のテスト（`npm test`、型検査）がすべて通る。
- 論文 300 本で、2 回目以降の単語帳の集計が 50 ms 以下、論文一覧・グラフ・検索がそれぞれ現状の半分以下。
- MCP サーバーの `tools/list` までの時間が、現状より pdf.js の読み込み分（約 150 ms 以上）短い。
- ファイルを外から書き換えた直後の読み取りに、新しい内容が反映される（テストで確かめる）。

### 今回やらないこと（理由）

- **Go への移行**: 上の結論のとおり。
- **pdf.js のワーカーを使い回す、文分割での pdf.js の 2 回読みをまとめる**: 1 本あたり 0.3〜0.8 s 縮む見込みがあるが、文分割の結果やメモリの扱いに影響する。取り込みは論文 1 本につき 1 回なので、別の変更として扱う。
- **`get_page_image` の JPEG 化**: PNG の変換（約 130 ms）が 17 ms ほどになるが、MCP の応答の形が変わる。
- **`DISABLE_SYSTEM_FONTS_LOAD`**: フォントを埋め込んでいない PDF の描画が変わるおそれがある。R1 で起動時にフォントを走査しなくなるので不要になる。

## 実装の結果

- R1: `server/pdfjs.ts` を通して、pdf.js を最初に使うときに読み込むようにした。
- R2: `Vault.memo`（任意）と `readMemo` を足し、`NodeVault` で実装した。目印は inode・更新時刻（ns）・大きさで、ファイル 4000 件まで覚える。使っているのは論文一覧の要約、検索用のノートの行、グラフと単語帳の注釈（`viewAnnotations`）、単語帳の用語集。`list_papers` の進み具合は `summarizeSentences` で、`sentences.json` と状態ファイルの目印が変わるまで使い回す（ready のときだけ）。
- R3: ブラウザ版の保管庫には `memo` が無く、`readMemo` は今までどおり毎回読む。

### 受け入れ基準の確認

- 論文 50 本のデータで、HTTP 15 本と MCP 9 本（`tools/list` を含む）の応答が、1 回目も 2 回目（キャッシュから返すとき）も変更前と完全に一致した。
- 型検査と `npm test`（273 件。今回足した `server/memo.test.ts` の 3 件を含む）が通った。E2E の 5 本も通った（smoke・server・slides・settings・help。Playwright 用のブラウザが無い Mac なので、入っている Chrome で動かした）。
- 外で書き換えたノートと `sentences.json` が、次の一覧・検索・単語帳にすぐ映ることを `server/memo.test.ts` で確かめている。

### 速度（論文 300 本、変更前と変更後を交互に起動した中央値）

| 項目 | 変更前 | 変更後 |
|---|---|---|
| ローカルサーバーの起動 | 340 ms | 163 ms |
| MCP サーバーの `tools/list` まで | 406 ms | 229 ms |
| 論文一覧 `/api/papers`（2 回目以降） | 97 ms | 10 ms |
| 単語帳・数式帳 `/api/lists`（2 回目以降） | 1112 ms | 86 ms |
| グラフ `/api/graph` | 255 ms | 51 ms |
| 検索 `/api/search`（該当なし、2 回目以降） | 294 ms | 25 ms |
| 検索 `/api/search`（該当あり） | 130 ms | 12 ms |
| MCP `list_papers`（2 回目以降） | 1962 ms | 20 ms |

- 単語帳の集計そのものは 23 ms になった（プロセス内で測った値）。`/api/lists` の 86 ms の残りは、8.6 MB の応答の JSON 化（約 20 ms）と転送にかかっている。
- 1 回目は、どのファイルも一度は読んで解析するため、今までと同じくらいかかる。
- MCP の `get_lists` を絞り込みなしで呼ぶと、論文 300 本では応答が 12 MB を超え、変更後も 4.5 s かかる。時間のほとんどは応答の JSON 化と受け渡しで、集計の速さではない。AI エージェントには `query` か `paper` で絞って呼ぶよう案内するのがよい。
