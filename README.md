# PaperLens

論文 PDF を読みながら、**1 文ごとの対訳**と、訳・用語・数式・読解メモを
**Markdown の保管庫（vault）** に残す、ローカルファーストな論文リーダー。

- 中央に原文 PDF、右サイドバーに 1 文ごとの日本語訳（対訳）と、選んだ箇所の訳・用語・数式・記録
- サイドバーの文と PDF 上の枠が双方向に連動する
- 全文の翻訳は **Claude を MCP 経由**で使う（翻訳 API キー不要・追加費用なし）
- データは保管庫フォルダの普通のファイル。Obsidian の保管庫としてそのまま開ける
- PDF は端末から出ない。サーバーは `127.0.0.1` にしか bind しない

PaperLens は、旧 LogiXiv（1 文単位の対訳リーダー）と、旧 PaperLens（読解ノートアプリ）を
1 つにまとめたもの。本体は `apps/reader`。Obsidian に似た画面（リボン・左右のサイドバー・
ステータスバー）の中に、旧 LogiXiv の文分割と対訳がそのまま入っている。

## なぜ「OSS のローカル実行アプリ」なのか

「Web アプリか OSS か」は二択ではない。OSS はライセンス、Web アプリは提供形態の話で、
PaperLens は **OSS の、ローカル実行アプリ**を採っている。画面は Web 技術で書き、
`127.0.0.1` のローカルサーバーが保管庫を読み書きする。その画面をブラウザで開くか、
Electron のウィンドウで開くかは利用者が選ぶ。

| 形態 | 判定 | 理由 |
| --- | --- | --- |
| SaaS（クローズド） | ✗ | 未公開論文を他人のサーバーに置く設計は研究室・企業で通らない |
| OSS + ホスト型 Web | ✗ | 結局 PDF がサーバーに上がる。運用コストを誰かが負う |
| **OSS + ローカル実行 Web** | **✓** | PDF が端末外に出ない / pdf.js が使える / 配布は git clone |
| OSS + デスクトップアプリ（Electron） | ○ | 提供している。中身は上の行と同じローカルサーバーと画面を、Electron のウィンドウで開くだけ。フォルダ選択ダイアログが使える代わりに、配布物は重い（Electron 一式を同梱する）。配布物（`npm run dist`）の作成は mac でまだ確かめていない |

以前は「Electron の重さに見合わない」として △ にしていた。判断を変えたのは、
保管庫フォルダを選ぶ・Finder で開くといった操作がブラウザからはできず、
日常使いの道具としては欠けていたため。重さの問題は残っているので、
ブラウザで開く形も同じ機能のまま残してある。

決め手は 3 つ。

1. 扱う対象が未公開原稿なので、`127.0.0.1` にのみ bind し、本文が外部へ出る経路をコードから消した
   （Host / Origin を確かめ、別のサイトからの操作も断る）
2. PDF 描画は pdf.js が圧倒的に強く、ネイティブで作り直す理由がない
3. 訳語の選び方・文の切り方は分野で好みが割れる。fork できること自体が実用価値になる

副作用として、翻訳を **Claude の MCP 経由**にできた。SaaS ならサーバー側で翻訳 API を叩き、
費用を誰かが負担し、本文が第三者の翻訳エンジンを通る。ローカル実行ならその全部が消える。

外へ出る通信があるのは、利用者が明示したときだけ。

- 設定画面で Claude の API キーを入れ、選んだ箇所の「訳す」「用語を調べる」「数式にする」を押したとき
  （送るのは選んだ範囲と前後の本文、題名。数式では選択範囲の画像も送る。PDF 全体は送らない）
- URL（arXiv など）を指定して論文を取り込んだとき
- GROBID を別のホストに置いたとき（既定は手元の Docker）

## 動かす

必要なのは **Node 22.6 以上**（`--experimental-strip-types` を使うため。`.nvmrc` あり）。

```bash
git clone https://github.com/nico0748/LogiXiv.git
cd LogiXiv
npm install
npm run build        # packages/* と apps/* をまとめてビルドする（初回は必須）
cd apps/reader
```

以降は `apps/reader` で実行する。

### デスクトップ版（普段使い）

```bash
npm run app          # ビルドしてから PaperLens のウィンドウを開く
```

保管庫は、初回は `apps/reader/data`。設定画面の「別のフォルダを選ぶ」で変えられる。
Obsidian の保管庫にしているフォルダを選んでもよい。

配布用のアプリ（.dmg / NSIS / AppImage）は `npm run dist` で `release/` にできる。
配布用のアプリでは保管庫の初期値が「書類」フォルダの `PaperLens` になる。

### ブラウザで開く

```bash
npm run build
npm start            # http://127.0.0.1:5175
```

ポートは `PAPERLENS_PORT` で変えられる。

### 開発中

```bash
npm run dev          # http://localhost:5173（/api は 127.0.0.1:5175 へ中継）
```

画面のコードは保存すると反映され、サーバーと MCP のコードを保存するとサーバーが再起動する。

`npm run build:single` で、サーバー無しで動く 1 枚の HTML（`dist-single/index.html`）も作れる。
ただしこの形では**対訳（GROBID による文分割）・MCP・保管庫の変更の自動反映は使えない**。

### 使い始める

1. 左端のリボンの「論文一覧」を開き（`⌘/Ctrl + \`）、PDF を取り込む（ドロップでもよい）。
   取り込むと、テンプレートから読解ノートを作り、裏で 1 文ずつへの解析を始める
2. 右サイドバーの「対訳」タブに文が並ぶ。PDF 上の枠を押すとその文のカードへ、カードを押すと PDF のその位置へ移る
3. 全文の訳は Claude に MCP 経由で頼む（下の「Claude から使う」）。訳は画面にすぐ反映される
4. PDF の文を選ぶと、マーカー・訳・用語・数式を記録できる。右の「訳」「用語」「数式」タブに一覧が出る
5. 「記録」タブに読解メモを書く。入力はそのまま `note.md` に保存される
6. リボンの「リスト」（`⌘/Ctrl + Shift + L`）で、全論文の用語と数式を 1 つの画面で引ける

### GROBID（強く推奨）

文の区切りと PDF 座標は GROBID から取る。無くても動くが精度は明確に落ちる。

```bash
docker compose -f docker/grobid.yml up -d      # http://localhost:8070
```

使うのは軽量な CRF 版（`grobid/grobid:0.9.1-crf`）。文の分割と座標付けはこれで実用になる。
精度が要るなら `-full`（Deep Learning 入り、GPU 推奨）に差し替えられる。

`PAPERLENS_GROBID_URL`（旧名 `LOGIXIV_GROBID_URL` も受け付ける）で別のホストを指せる。
GROBID に届かないときは pdf.js による簡易解析に自動で切り替わり、その旨が
「対訳」タブのバッジ・ステータスバー・`parserNote` に出る。
「対訳」タブの「解析し直す」で、自動 / GROBID / 簡易解析を選んでやり直せる。
再解析しても訳・メモ・用語集・区切りの直しは消えない（後述の正規化ハッシュで結び直す）。

#### 簡易解析で何が起きうるか

簡易解析は当たり外れがある。よく当たるが、**2 段組の左右が語単位で噛み合う**ことがある。

```
"Standard Retrieval-augmented systems concatenate dozens of doc-
 attention computes uments into a single prompt, and agentic systems accu-"
```

こうなると原文そのものが壊れているので、`fix_sentence_boundary`（結合・分割）では戻せない。
GROBID を立てて再解析するのが唯一の道になる。

もう 1 つ、**本文が黙って消える**ことがある。数式を含む行を本文から外す判定が
効きすぎると、段落が丸ごと落ちたうえで残骸が文法の通る英文に癒着する。
そうなると Claude はもっともらしい日本語に訳し、読者には「論文がそう書いてある」
としか見えない。**消えたという情報がゼロである点で、これがいちばん危ない。**

**どちらも自動で検出して申告する。**

| 申告 | 何を見ているか |
| --- | --- |
| 読み順に崩れの疑い | 生き残った本文行の中に、段間相当の空白が残っているか |
| 本文の欠落の疑い | 行になった文字のうち、行き先（本文・柱・参考文献など）の説明が付いた割合 |

**別建てにしてあるのは、消えた行が読み順の検査に入らないから**（生き残った行しか
走査しないので、消去は原理的に見えない）。どちらも「対訳」タブのバッジ・`parserNote`・
MCP の `caveat` に出る。検出されないこと（`low`）は
崩れが無いことの保証ではないが、少なくとも**崩れているのに黙っている**状態は無くしてある。

精度そのものは（リポジトリの最上位で）`npm run measure` で測っている。合成 PDF 14 本に加えて、
`pdflatex` / `xelatex` で組んだ実物の論文 6 本（`scripts/real-papers/`）を
正解つきで通す。正解は `.tex` から機械生成し、PDF から取り出した結果は使わない。

この計測器は 2 度作り直している。

- 合成 PDF だけを測っていた頃は、実物の壊れ方を 1 つも再現できないまま
  「14 シナリオすべて 100%」と表示していた
- 実物を足した後も、その実物の**中身から数学が抜けていた**（`onecolumn.tex` には
  `$` が 1 つも無かった）。ML・統計・物理の論文は技術的な段落のほぼ全行に
  ギリシャ文字か添字が入るので、壊すものを取り除いた標本で 100% を出していた

いまは数学の濃い版（`mathheavy`）と和文 2 本（1 段組・2 段組）を含む。

### Claude から使う（MCP）

**設定画面（リボン下の歯車）の「AI エージェント（MCP）」を開くのが確実。**
この端末の絶対パスが入った登録方法が出るので、「コピーする」で貼ればよい。
以下は同じことを手で書く場合の説明。`<apps/reader>` は実際のパスに置き換える。

Claude Code なら 1 行で済む。

```bash
claude mcp add paperlens -e PAPERLENS_CONFIG=<apps/reader>/paperlens.config.json -- node <apps/reader>/dist-server/mcp.js
```

Claude Desktop なら、設定ファイルの `mcpServers` に足して、**Claude Desktop を起動し直す**。

| OS | 場所 |
| --- | --- |
| macOS | `~/Library/Application Support/Claude/claude_desktop_config.json` |
| Windows | `%APPDATA%\Claude\claude_desktop_config.json` |
| Linux | `~/.config/Claude/claude_desktop_config.json` |

```json
{
  "mcpServers": {
    "paperlens": {
      "command": "node",
      "args": ["<apps/reader>/dist-server/mcp.js"],
      "env": { "PAPERLENS_CONFIG": "<apps/reader>/paperlens.config.json" }
    }
  }
}
```

デスクトップ版は設定ファイルをアプリのデータフォルダに置くので、
`PAPERLENS_CONFIG` の値は設定画面に出るものを使う。

MCP サーバーは保管庫のファイルを直接読み書きするので、**アプリを起動していなくても使える**。
アプリを開いていれば、Claude の書き込みは画面にすぐ反映される。

全文を訳すときは、Claude に「PaperLens の論文 ○○ を全文訳して」と頼めばよい。
`translate_paper` プロンプトに手順がまとめてある
（`get_sentence_outline` → `get_translation_batch` → `set_translations` を、`remainingUnique` が 0 になるまで繰り返す）。
段階を追って読解ノートを埋める `read_paper`、読んだ論文を横断してふり返る `review_notes` もある。

`PAPERLENS_MCP_READONLY=1` を付けると読み取りのツールだけを公開する。
ツールの一覧と設計は [docs/mcp.md](docs/mcp.md)。

### 文の数え方（「202 文」と言いながら 273 行あるとき）

訳は**文そのもの**ではなく**本文の正規化ハッシュ**に付く。同じ本文が
Introduction と Results に出てくれば、1 件の訳が両方に反映される。だから

- 進捗の数（`訳 3/202`）は**異なり文**の数（＝作業量）
- サイドバーに並ぶのは**延べ**の行数

で、後者の方が多くなる。2 回目以降の出現には「同じ本文が前にも出ています」と印が付く。

## 画面

```
┌──┬────────────┬───────────────────────────┬──────────────────────────┐
│論│ 論文一覧    │ [論文の題名]  ← タブの見出し │ 対訳 | 訳 | 用語 | 数式 | 記録 │
│検│ （既定は閉） │                           │                          │
│リ│            │  PDF（pdf.js）              │ 1 文ずつのカード            │
│グ│            │  文の枠・マーカー            │ 訳・メモ・区切りの直し       │
│  │            │                           │                          │
│設│            │                           │                          │
│？│            │                           │          ステータスバー     │
└──┴────────────┴───────────────────────────┴──────────────────────────┘
```

- **リボン**（左端）: 論文一覧 / 検索 / リスト / グラフ、下に設定 / ヘルプ
- **左サイドバー**: 論文一覧と、読解ノートの横断検索。**既定では閉じている**（`⌘/Ctrl + \`）
- **中央**: タブの見出しの下に PDF。「文の枠」を出すと、対訳の文が PDF 上に重なる
- **右サイドバー**: 対訳（1 文ずつの訳・メモ・訳さない記録・区切りの直し・用語集）/
  訳（選んだ箇所のマーカーと訳）/ 用語 / 数式 / 記録（テンプレートの記録欄）
- **ステータスバー**: 保存の状態と、開いている論文の解析方式（GROBID / 簡易解析）・訳の進み具合
- **リスト**: 広いモーダル。**単語帳**（各論文の用語と、対訳の用語集）と**数式帳**を、全論文から集めて引ける
- **グラフ**: 論文と用語のつながり

サイドバーの開閉と幅は保管庫の `.paperlens/workspace.json` に保存し、次に開いたときに戻す。

## 保管庫

保管庫（保存先フォルダ）は次の順に決まる。

1. 環境変数 `PAPERLENS_DATA`
2. 設定ファイル（`PAPERLENS_CONFIG`、無ければ `apps/reader/paperlens.config.json`。デスクトップ版はアプリのデータフォルダ）の `dataRoot`
3. 初期値（`apps/reader/data`、配布版は「書類」の `PaperLens`）

```
<保管庫>/
├── .paperlens/workspace.json        画面の配置（サイドバーの開閉・幅・開いている論文）
├── _templates/reading-note.md       読解ノートのテンプレート
└── papers/<論文ID>/
    ├── paper.pdf                    取り込んだ PDF
    ├── note.md                      読解ノート（テンプレートから作る）
    ├── paperlens.json               マーカー・用語・数式（位置などの補助データ）
    ├── sentences.json               1 文ずつの対訳（構造 + 注釈）
    └── sentences.status.json        解析の進み具合（解析中 / 失敗 / 完了と警告）
```

DB は無い。「アプリを捨ててもデータが読める」ことを優先している。
書き込みは一時ファイル → rename。Obsidian で `note.md` を書き換えても画面にすぐ反映される。
テンプレートの書き方は [apps/reader/README.md](apps/reader/README.md)。

## 技術的な中核 — なぜ「1 文ごと」が成立するか

GROBID に `segmentSentences=1` と `teiCoordinates=s` を付けて投げると、
**文単位で PDF 座標が付いた TEI** が返る。

```xml
<s coords="1,53.80,194.57,238.71,9.29;1,53.80,205.00,238.71,9.29">
  We study sparse attention under long contexts.
</s>
```

`page, x, y, w, h`（PDF ユーザー空間・左上原点）。行またぎの文には矩形が複数付く。
この座標に pdf.js の描画結果を重ねると、文と枠が 1 対 1 で対応する。
**ここだけは自前のテキスト抽出で代替できない**（2 段組・ハイフネーション・数式・脚注で必ず壊れる）。

## 構成

```
apps/reader       PaperLens 本体。画面（React）・ローカルサーバー・MCP サーバー・デスクトップ版（Electron）
packages/core     型・TEIパーサ・文分割・検証・エクスポート/インポート・マージ・移行（唯一の真実、外部依存ゼロ）
packages/server   GROBID 呼び出しと pdf.js による簡易解析（ワーカースレッド）。旧 LogiXiv Web 版のローカル API もここ
packages/mcp      旧 LogiXiv Web 版の MCP サーバー
apps/web          旧 LogiXiv の Web UI（単一 HTML の書き出し・取り込みのために残している）
apps/viewer       書き出しHTMLに埋め込む単一ファイルビューア（pdf.js 同梱）
```

`sentences.json` の中身は `packages/core` の `PaperDocument` そのもので、
文分割・正規化ハッシュ・再解析時の結び直しは旧 LogiXiv と同じコードを使っている。

### 旧 LogiXiv の Web UI（apps/web）について

PaperLens 本体には、まだ**対訳を単一 HTML に書き出す機能と、その HTML を取り込む機能が無い**。
それが要るときは旧 LogiXiv の Web UI を使う（PaperLens 側へ移すまでの措置）。

```bash
npm start          # リポジトリの最上位で。http://127.0.0.1:4173
```

Web UI のデータは保管庫ではなく、別の置き場（`~/.paperlens-server/documents/<id>/`。
旧 LogiXiv の `~/.logixiv/` だけがあるときはそちらを使い続ける）に入る。
PaperLens の保管庫との間で自動では行き来しない。
環境変数は `PAPERLENS_SERVER_PORT` / `PAPERLENS_SERVER_DATA_DIR` など（旧名 `LOGIXIV_*` も受け付ける）。

## 主要な設計判断

- **構造データと注釈を分離した。** 再解析で訳が消えないよう、原文の正規化ハッシュで再結合する
- **正規化で文字間のハイフンを落とす。** GROBID の `block-sparse` と、行末で割れた `block-` + `sparse` を
  同じハッシュにするため。これが無いと「GROBID を後から入れて再解析」で訳が外れる
- **メモは衝突しても消さない。** 訳は「正解が 1 つ」だがメモは「多いほど良い」。マージ規則を非対称にした
- **人手修正フラグ。** `revisedByHuman` が立った訳を機械が上書きしない
- **注釈は操作として書く。** `paperlens.json` は丸ごと上書きせず、追加・更新・削除の操作を、
  書く直前に読み直した最新に当てる。画面と Claude が同時に書いても互いの変更を消さない
- **解析の状態をファイルに置く。** 画面のサーバーと MCP サーバーは別プロセスなので、
  「解析中」「失敗した」を `sentences.status.json` に書いて互いに見えるようにした
- **取り込む JSON は全部検証する。** `sentences.json` も読み出し時に検証・移行し、
  型が合わない要素は落とす。壊れて読めないファイルは捨てずに `sentences.corrupt-<時刻>.json` へ退避してから作り直す
- **PDF 解析はワーカースレッド。** pdf.js は Node では同一スレッドで動くので、
  大きな PDF 1 本でサーバー全体が数十秒止まっていた。同時に回す解析は 2 本まで
- **フォールバックでもレイアウトを読む。** 段組を検出してから行を組むので、
  2 段組で左右が混ざらない。柱・ノンブル・図表キャプション・数式・参考文献は本文から外し、
  節見出しも拾う（`npm run measure` で 2 段組の再現率 100% / 混入 0 を確認している）
- **「訳さない」を記録できる。** 参考文献の断片のように訳す対象でないものを
  飛ばすだけだと、翻訳の手順が永久に終わらない
- **`consolidateHeader=0`。** GROBID の既定値 1 は CrossRef へ問い合わせに行く。未公開原稿のタイトルを外部に出さない

詳しくは [docs/architecture.md](docs/architecture.md) と [docs/mcp.md](docs/mcp.md)。

## テスト

```bash
npm run typecheck   # 全パッケージ（apps/ 含む）の型チェック
npm test            # core・server・apps/reader のユニット/API テスト
npm run test:e2e    # 旧 Web 版の取り込み→翻訳→SSE→書き出し→取り込み→MCP 起動の通し確認
npm run measure     # 論文風 PDF を生成して、解析の再現率と混入率を実測
```

PaperLens 本体の画面の通し確認は `apps/reader` の `npm run e2e`（ヘッドレス Chromium）。

`npm run measure` は「正解が分かっている論文風 PDF」（2 段組・柱・ノンブル・図表
キャプション・数式・参考文献つき）を生成して解析にかけ、本文の再現率と
本文以外の混入数を出す。再現率 90% 未満か混入 2 件以上で失敗する。

`test:e2e` は GROBID が居ない前提で走り、フォールバック経路を通す。
GROBID を上げた状態で確認したいときは `PAPERLENS_GROBID_URL` を指定する。

## 既知の制約

- スキャン PDF（画像のみ）は扱えない。先に OCR を通す必要がある
- 対訳の単一 HTML への書き出し・取り込みは、まだ旧 Web UI（`apps/web`）にしか無い
- 書き出し HTML は大きい（PDF + ビューア約 1.8MB）。PDF 100MB 超は書き出せない
- 特殊な CropBox で座標がずれ得る
- フォールバック経路の枠は**行単位**。1 行に 2 文あると両方が同じ範囲で光る
  （GROBID 経路は文単位の座標なのでこの制約は無い）
- `sentences.json` への書き込みを順番に並べるのは、同じプロセスの中だけ。
  画面のサーバーと MCP サーバーは別プロセスで、どちらも書く直前に読み直すが、
  プロセスをまたぐ排他は無い。同じ論文の対訳を、画面と Claude がまったく同時に書き換えると、
  片方の変更が消えうる

### 簡易解析で、まだ黙って壊れうるもの

自己申告（「読み順に崩れの疑い」「本文の欠落の疑い」「継ぎ目の印」）は、
**検出できたものだけ**を言う。以下は検出の網の外にあると分かっている。

- **移動した断片が、次の文に取り込まれた場合。** 継ぎ目の印は「その断片を抱えた文」に
  付くので、**記号が抜けた文そのものではなく 1 行下に付く**ことがある。
  実例: `E∥ē∥2 ≥ η2(1 − δ)ζ2, as claimed.`（正しくは `≥ (η²(1−δ)/4) ζ²`）は無印で、
  印は移動先の `The constant 1/4 is not t 4 optimised.` に付く。
  画面では隣り合うので「このあたりが壊れている」は伝わるが、その文自身は黙っている
- **インライン分数が本文の半分近くを占める節では、文が丸ごと落ちることがある。**
  `coverage` は 100% のまま。ただし残るのは主語の無い断片なので、読めば壊れていると分かる
- **継ぎ直せない断片（1〜2 文字）の中身は渡せない。** 印と場所は出るが、
  「抜けたのはここ」には出ない（`4` とだけ出しても読む側に何も与えないため）
- **柱間が 8pt を下回る組**（LaTeX の既定は 10pt）では段の切れ目が語間と区別できない。
  6pt 以下でも「読み順に崩れの疑い」は出るが、直せない
- **回転した組みと通常の本文が同じページにあるとき**、どちらを本文とみなすかは
  字数で決める。横倒しの大きな表が本文より字数の多いページでは、判断を誤りうる
  （そのときは本文が「訳しません」側に出る。消えはしない）

いずれも GROBID を立てて再解析すれば解消する。
- 柱が本文ブロックに密着している組み方では、柱が 1 文として残ることがある
  （本文の 1 行目を消すよりは害が小さい、という寄せ方）
- 1 ページだけの文書では柱を落とせない（同じ行が複数ページに出るかで判定するため）
- フォールバック解析は 400 ページで打ち切り、120 秒を超えたら中止する（それ以上は GROBID を使う）
- 正規化の副作用として `re-cover` と `recover` は同じハッシュになる
- 文末記号が 1 つも無い文書では、1 文 4,000 字で機械的に割る
  （欧文は語の切れ目、和文は約物か和欧文の境目で切る）
